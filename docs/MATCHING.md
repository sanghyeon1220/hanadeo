# 하나더 매칭 알고리즘 — 보고서 모델을 직접 이해하기 위한 정리

이 문서는 프로젝트 보고서 3~8장의 설계를 **코드가 실제로 어떻게 계산하는지** 연결해 설명합니다.
종이와 계산기로 따라 할 수 있게 썼습니다. ✍️ 표시는 발표 질의응답 대비용 질문이니 직접 답을 적어 보세요.

## 2. 동적 가격 (보고서 5장)

```
P_s(t) = P_min + (P_0 − P_min) × (1 − t / T)
```
- t = 등록 후 경과시간, T = 등록부터 판매 종료까지(전체 판매 가능시간)
- t ≥ T 이면 최저가로 고정하고, 판매가 종료되어 후보에서 빠집니다.

보고서 5.3 표(4,000원 → 2,000원, 72시간)는 테스트로 고정되어 있습니다: 0h 4,000 / 24h 3,333 / 48h 2,667 / 72h 2,000.

## 3. 5변수 매칭점수 (보고서 6~7장)

```
M = 100 × (0.30·P + 0.25·D + 0.20·T + 0.15·R + 0.10·U)
```

| 변수 | 식 | 값의 범위 |
|---|---|---|
| P 가격 | `max(0, 1 − 0.5 × P_s / B)` | P_s ≤ B 이므로 **0.5 ~ 1** |
| D 거리 | `max(0, 1 − d / 1.5)` | 0 ~ 1 (1.5km 이상 0) |
| T 거래시간 | `min(1, 겹친 분 / 60)` | 0 초과 ~ 1 (안 겹치면 후보 제외) |
| R 신뢰도 | `(완료 + 1) / (종료 전체 + 2)` | 0 초과 ~ 1 미만 (신규 0.5) |
| U 긴급도 | `긴급도 / 5` | 0.2 ~ 1 |

### 3.1 손으로 계산해 보기 — 실제 서버가 낸 값

로컬 DB 시나리오에서 판매자가 받은 추천 1위(학생B)입니다.
- 상품: 4,000 → 2,000원, 72시간 중 24시간 경과 → P_s = 2000 + 2000 × (1 − 24/72) = **3,333원**
- 학생B: 예산 3,500원, 같은 장소(0km), 30시간 겹침, 거래 이력 없음, 긴급도 4

1. P = 1 − 0.5 × 3333/3500 = 1 − 0.4761 = **0.5239**
2. D = 1 − 0/1.5 = **1**
3. T = min(1, 1800/60) = **1**
4. R = (0+1)/(0+2) = **0.5**
5. U = 4/5 = **0.8**
6. M = 100 × (0.30×0.5239 + 0.25×1 + 0.20×1 + 0.15×0.5 + 0.10×0.8) = 100 × 0.7622 = **76.22점** ← 서버 결과와 같음

판매자가 학생B를 노쇼로 신고하면 B의 이력은 완료 0 / 종료 1 → R = 1/3 → **73.72점**으로 내려갑니다(서버에서 확인).

✍️ 학생C(예산 4,000원, 0.319km, 30분 겹침, 이력 없음, 긴급도 2)의 점수를 계산해 보세요. (서버 값 58.69)

### 3.2 신뢰도 R 의 계산 규칙 (구현하면서 정한 것)
- **종료된 거래** = 완료 + 구매자 본인이 취소한 거래 + 노쇼. **판매자가 취소한 거래는 구매자 책임이 아니므로 세지 않습니다.**
- 노쇼는 판매자만 신고할 수 있습니다.
- `(성공+1)/(전체+2)` 는 **라플라스의 계승 규칙(rule of succession)** 이라는 이름이 있는 식입니다. 이력이 적을 때 극단값(0 또는 1)이 나오지 않게 해 줍니다. 1전 1승이면 1.0이 아니라 0.67입니다.

✍️ 신규 이용자(0.5)가 1번 완료하면 0.67이 되고, 1번 취소하면 0.33이 됩니다. 이 불이익이 너무 크지는 않을까요? (보고서 6.4 "향후 개선" 항목)

## 4. 가중치·스케일 검증 (교수님 피드백)

### 4.1 이름상 가중치 vs 실제 영향

가상 상품 20개 × 구매자 30명 데이터로, 상품마다 **후보 구매자 사이에서 각 변수가 만드는 점수 차이(최대−최소)** 를 쟀습니다(`effectiveSpread`, 발표 화면에 실시간 표시).

| 변수 | 이름상 가중치 | 실제 차이 (20개 상품 평균) | 범위 |
|---|---|---|---|
| P 가격 | 30 | **2.9점** | 0.7 ~ 5.7 |
| D 거리 | 25 | **19.6점** | 11.2 ~ 25.0 |
| T 거래시간 | 20 | **2.0점** | 0 ~ 10.0 |
| R 신뢰도 | 15 | 7.2점 | 2.0 ~ 10.0 |
| U 긴급도 | 10 | 6.8점 | 2.0 ~ 8.0 |

**해석:**
- **P가 가장 큰 가중치(30%)인데 실제 영향은 거의 가장 작습니다.** P = 1 − 0.5·P_s/B는 P_s ≤ B라서 항상 0.5~1 사이입니다. 이론상 최대 차이가 15점이고, 실제로는 판매자 한 명의 상품(같은 P_s)에 대해 구매자 예산 B만 다르기 때문에 차이가 더 작아집니다.
- **D가 사실상 순위를 결정합니다.** 거리는 0~1 전체 범위를 다 쓰기 때문입니다.
- **T는 대부분 0점입니다.** 60분만 겹쳐도 만점이라 대부분의 후보가 T = 1입니다.
- 즉 "가격 30%, 거리 25%"라고 발표하면 실제 동작과 다릅니다. **가중치의 의미는 변수의 범위(스케일)와 함께 정해집니다.**

✍️ 발표에서 이 표를 보여주고, 아래 중 무엇을 할지 **직접 정해 보세요**(코드는 보고서 식 그대로 두었습니다).
1. P 식을 바꾸기. 예: `P = (B − P_s) / B` (0~1 전체 범위). 다만 이 경우 P의 의미가 "예산 대비 절약 비율"로 바뀝니다.
2. 식은 두고 가중치를 조정하기
3. 식과 가중치를 그대로 두고, "실제 영향은 거리 중심"이라고 한계를 밝히기

✍️ 판매자 관점에서 P_s는 모든 구매자에게 같으니, P가 높다는 것은 **예산이 큰 구매자**라는 뜻입니다. "더 많이 낼 의향이 있는 구매자를 우대한다"는 것이 의도한 설계인가요?

### 4.2 "한 단위는 몇 점인가"로 가중치 읽기
- 거리 100m = **1.67점**
- 겹치는 시간 10분(60분까지) = **3.33점**
- 긴급도 1단계 = **2점**
- 신규(0.5) vs 5전 5승(0.86) = **5.4점**

→ "긴급도를 1단계 올리는 것 = 약 120m 더 가까운 것"과 같은 점수입니다. 이 교환이 상식적인지 설문으로 확인할 수 있습니다(4.4).

### 4.3 민감도 분석
가중치를 각각 ±30% 범위에서 무작위로 300번 흔들었을 때(`sensitivity`):
- 20개 상품 중 17개는 1위 유지율이 95% 이상이고, TOP 3 구성도 대부분 90% 이상 유지됩니다.
- **판매자 B(바나나), I(우유), O(컵라면)는 1위 유지율이 64~69%** 입니다. 1·2위 점수 차이가 작아서, 가중치 가정에 따라 추천 1위가 바뀝니다.
- 이렇게 **"어떤 경우에 가중치 선택이 결과를 바꾸는지"를 숫자로 말할 수 있다는 것**이 타당성 검증입니다.

### 4.4 가중치를 데이터로 검증하는 방법 (보고서 "추후 설문으로 검증" 구체화)
친구 15~30명에게 짝 비교 문항 5~8개를 받아 보세요. 예:
> 판매자 입장에서 누구와 거래하겠습니까?
> A: 300m 거리, 신뢰도 0.5(신규), 긴급도 5 / B: 700m 거리, 신뢰도 0.9, 긴급도 2

각 문항에서 다수가 고른 쪽과 우리 점수가 더 높은 쪽이 **일치하는 비율**을 재면 됩니다. 일치율이 낮은 문항을 보면 어떤 가중치가 어긋났는지 알 수 있습니다. 가장 간단한 형태의 **컨조인트 분석**입니다.

## 6. 구매자 우선순위 설정

구매자는 구매 요청을 만들 때(또는 상품 둘러보기의 "내 우선순위 바꾸기"에서) 5개 변수의 순서를 정할 수 있습니다.

- **가중치 변환:** 보고서 가중치 값 30·25·20·15·10%를 그대로 두고, 구매자가 정한 1~5순위에 차례대로 배정합니다(`weightsFromPriority`).
  예) 거리 > 가격 > 시간 > 신뢰도 > 긴급도 → D 30%, P 25%, T 20%, R 15%, U 10%
- **적용 범위:** 구매자 본인이 보는 **상품 추천 순서와 "내 기준" 점수에만** 적용합니다.
- **판매자 TOP 3와 서버에 저장되는 매칭점수는 항상 보고서 기본 가중치**로 계산합니다. 구매자마다 다른 식을 쓰면 자기에게 유리한 항목(예: 자기 신뢰도가 높으면 R)을 1순위로 올려 점수를 부풀릴 수 있고, 판매자가 구매자들의 점수를 공정하게 비교할 수 없기 때문입니다. 테스트 "판매자 TOP 3 는 구매자가 우선순위를 바꿔도 같은 점수"가 이를 확인합니다.

**알아둘 점**
- 구매자 화면에서 **R(내 거래 이력)과 U(내 긴급도)는 모든 상품에 같은 값**입니다. 그래서 이 둘을 위로 올리면 상품 순서가 바뀌는 게 아니라, 가격·거리·시간의 비중이 함께 줄어듭니다.
- 발표 화면 예시(학생01, 바나나): 기본 순서에서는 A(0km, 3,333원) > D > C 순입니다. "가격 > 시간 > 신뢰도 > 긴급도 > 거리"로 바꾸면 C(0.61km, 2,200원) > D > A로 **순위가 뒤집힙니다**.
- 반대로 체험 모드의 콜라 예시는 가격을 1순위로 올려도 순서가 바뀌지 않고 점수 차이만 줄어듭니다(78.1 / 68.0 → 71.6 / 69.8). 4.1절에서 본 것처럼 **P 식의 범위가 0.5~1로 좁아서** 가격 비중을 높여도 효과가 제한적입니다.

✍️ 구매자가 우선순위를 정하는 것은 보고서의 "가중치는 가정값" 문제를 해결하는 방법일까요, 아니면 피하는 방법일까요? (힌트: 판매자 쪽 점수는 여전히 가정값입니다)

## 7. 확장: 할당 문제 (보고서 범위 밖)

판매자마다 TOP 3를 따로 추천하면 **같은 구매자가 여러 상품의 1위**가 될 수 있습니다. 먼저 선택한 판매자가 그 구매자를 데려가면 다른 판매자는 차선책만 남습니다.
판매글 j와 구매요청 i를 1:1로 짝지어 점수 합을 최대로 만드는 문제가 **할당 문제**입니다.

```
최대화   Σ M_ij · x_ij
조건     구매요청 하나는 상품 하나까지, 상품 하나는 구매자 한 명까지, 필터 탈락 쌍은 0
```

**헝가리안 알고리즘**이 이 문제를 O(n³)에 정확하게 풉니다(`src/lib/assignment.js`).
1. 비용 행렬의 행마다, 열마다 최솟값을 뺍니다. 모든 배정의 총비용이 같은 양만큼 줄어드니 최적해는 그대로입니다.
2. 0인 칸만으로 1:1 배정이 되면 그것이 최적입니다.
3. 안 되면 0을 최소 개수의 선으로 덮고, 덮이지 않은 칸의 최솟값만큼 조정해 0을 늘립니다. 이를 반복합니다.

✍️ 손으로 풀어 보세요 (최소비용, 정답 5).
```
4 1 3
2 0 5
3 2 2
```

가상 데이터(상품 20 × 구매자 30) 결과:

| 방법 | 성사 | 점수 합 |
|---|---|---|
| 선착순 (먼저 요청한 구매자가 고름) | 20건 | 1,462.0 |
| 점수 높은 쌍부터 확정 | 19건 | 1,426.4 |
| **헝가리안 최적** | **20건** | **1,493.5** |

테스트는 무작위 행렬 300개에서 헝가리안 결과가 완전탐색(모든 경우 다 해 보기)과 같은지 확인합니다.
실제 앱은 아직 보고서대로 **판매자가 TOP 3 중에서 직접 고르는 방식**입니다. 일괄 배정은 "제안" 형태로 붙일 수 있는 다음 단계입니다.

✍️ 판매자가 직접 고르는 방식과 일괄 최적 배정은 각각 어떤 장단점이 있을까요? (힌트: 판매자의 선택권, 즉시성, 전체 효율)

## 8. 구현하면서 단순화한 것 (발표 때 밝힐 것)
- 수량: 구매 희망수량이 판매 수량 이하인지 필터만 합니다. 한 판매글은 한 구매자와 매칭되며, 일부 수량만 나눠 파는 기능은 없습니다.
- 거리: 직선거리(하버사인)이며 실제 도보 거리가 아닙니다. 장소 좌표는 지도에서 대략 잡은 값입니다.
- 거래 방식(직거래/문고리)과 상품 상태는 저장·표시만 하고 점수에는 넣지 않았습니다(보고서 6장에도 없음).
- 신뢰도는 누구나 조회할 수 있는 공개 지표로 설계했습니다(거래 횟수만 공개, 개별 거래 내용은 비공개).
